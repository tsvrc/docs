## Purpose

The reference pages under `docs/tsvrc/` are accurate and thorough (see
`TSVRC-VERIFICATION-TRACKER.md`) but explain behavior without showing what calling the thing
actually looks like. This pass adds that, following patterns confirmed by researching
React, MDN, and Stripe's own docs (see conversation for the research writeup):

- Examples live **on the same reference page**, in a `## Usage` section — no separate
  "examples" doc tree.
- 1-3 short snippets per page: the minimal case, then (only if genuinely useful) one
  realistic edge case or twist. Not a kitchen-sink tour of every option.
- When two pages would need near-identical setup code, show it in full once (on whichever
  page owns the concept) and link the others to it instead of re-pasting it.
- No filler prose around the snippets — a one-line lead-in, the code, done. The snippet
  should be self-explanatory to someone who already read the rest of the page.
- Every snippet uses invented generic names (a "world", "GameManager", "LeaderboardController",
  etc.), grounded in real usage patterns found in the private consumer project referenced by
  the MoL rule in `TSVRC-DOCUMENTATION-PLAN.md` — **that rule applies identically here**: the
  project is never named, quoted, or made identifiable in anything written to these docs.
- A handful of genuinely multi-type recipes don't belong on any single reference page — those
  become new task-oriented how-to guides under a new `docs/tsvrc/how-to/` folder, not usage
  snippets bolted onto one type's page.

## Quality bar (checked per page before marking done)

- [ ] Does the snippet compile in spirit (right method names, right types, right call shape)?
- [ ] Is it the *minimal* version of the pattern, not padded with unrelated setup?
- [ ] Does it avoid restating the prose already on the page?
- [ ] Zero MoL-identifying content (names, paths, class names, project identity)?
- [ ] `npm run build` still clean after the edit?
